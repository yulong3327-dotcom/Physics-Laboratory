# 生产流程梳理与优化（2026-09-15）

## 现有流程与证据

确认讲稿 → AI 全课结构 → 按教学段分批生成 → 电路画面准备 → 确认分镜 → 全课静态预检 → 配音及真实时间轴 → 渲染 → 自动验收。

- 每批最多 3 段台词、600 字，逐批等待；请求批量与每页 1–3 句的画面设计混在一起。
- 每批重复全课逐句正文、制作备注、规划和既有电路。离线检查内置 29 段样课：首批正文 203 字，请求体 34,193 字节，默认共 10 批。
- 用户 65 段课程的最后一次分镜任务耗时 723 秒，继承的断点累计 42 次 AI 请求、0 次网络重试；分镜细化累计 1,161.772 秒，最终因镜头板式无效失败。累计值含此前任务的工作，不能当作本次耗时。
- 传输最多尝试 3 次；内容错误再允许最多 2 次纠正。服务器的输出截断没有进入现有拆批路线。
- 部分合并错误延至全部生成后检查。已有断点可以复用，但界面创建相同的 waiting_retry 任务时没有真正 resume。
- 时间轴按钮强制创建新预检；全课预检与分镜共用任务队列。配音服务故障是独立问题，不能靠重复生成分镜解决。

## 本轮实施顺序

1. 保留先规划、再有序细化的结构；共享电路、公式引用和断点依赖不做无界并发。
2. 服务器默认按 6 段/1000 字安排一次请求，可同时细化相邻几个教学段。每个镜头仍只能属于一个教学段、引用该段规划的电路；请求批量与教学分页独立。旧断点保留原批次。输出截断递减拆批；明确超时最多拆一层，限制随断点保存。鉴权、限流和其他网络失败不额外拆批。
3. 有全课规划时，发送章节摘要、本批涉及教学段的台词 ID 映射、邻近台词和必要引用；制作备注与审核信息只保留一份，既有电路只发送相关教学段所需的并集。完整电路快照仍用于合并和检查。原题图始终保留，已有拓扑不能证明图中所有条件已经转写。
4. 每批提交断点之前检查与已有分镜合并后的内容，并使用与生产接口一致的严格字段、公式、板式规则，把镜头/对象定位反馈给当前批次。恢复旧断点也执行同样检查；只有明确的未来公式引用可以等后续批次，最终仍执行完整校验。
5. 分别记录每次请求的耗时、输入/输出体量、用量、重试及批次进展，让慢在何处可以量化。
6. 修复点击继续、完成结果复用、最新任务排序以及时间轴不必要的强制重做。
7. Fish 配音按同一条台词的独立音频片段以 2 路小窗口处理，按原顺序拼接实测 PCM；成功片段即时缓存，相同片段去重并兼容旧缓存。429 或临时故障共享最长退避期限并降为串行，最终失败停止新请求，收尾已在途片段。同步时间仍来自真实采样，没有按字数猜时间。
8. 跑已有回归测试、构建和隔离的实际生成验证；记录实测与仍依赖外部服务的限制。

## 验收重点

讲稿不改写；台词完整且严格按序覆盖；章节边界不混用；已完成批次恢复；取消和中断安全；截断拆批；限流不额外拆批；跨批公式与电路引用；内容错误不得通过放宽校验隐藏。

## 验证结果与实际限制

- 同一份 65 段、2459 字、20 个教学段的原始输入：基础细化请求由 **31 批变为 11 批**，减少约 65%；另有一次全课规划，不含内容纠正和拆批。旧任务恢复仍沿用已有批次，不为获得新批量重做成功内容。数据见 `artifacts/production-optimization/batch-comparison.json`。
- 使用真实历史失败断点隔离恢复：**65 段/35 镜头在 858ms 内通过，AI 请求为 0**。结果存于 `history-recovered-project.json`，用户正在编辑的工程和原任务记录未被覆盖。
- 真实网关测试观测到单次请求 34–89 秒，且曾在完成 6/8 段后连接中断；前 6 段断点保留。说明外部模型和网关延迟仍是主瓶颈。
- 最终跨教学段合批实测成功：同一请求范围包含 2 个教学段、2 段台词；首次内容未通过检查，反馈纠正后得到 2 镜头并通过完整校验，旁白不变。总计 2 次细化请求、138.754 秒，复用了已有规划；不是新任务端到端耗时。见 `short/cross-section-summary.json`。这一样本**不能证明墙钟耗时下降 65%**。
- Fish 并发的离线测试校验了真实 WAV 顺序、采样时间、失败恢复、旧缓存迁移，以及两个线程分别收到 7/11 秒 Retry-After 时遵守最长截止时间、降级后并发为 1。模拟 10 个各 50ms 的片段为串行 512.6ms、两路 255.7ms；未将这个模拟数值当作真实服务速度。
- 最终 **550 项 TypeScript 测试通过**，生产构建通过；41 项 Python 配音/时间轴/故障回归及 2 项浏览器恢复/复用用例通过。一次与构建并行的全量测试中，已有 Windows 硬退出测试未收集到子进程输出；该用例单独复查及随后完整 550 项重跑均通过，未修改或跳过该测试。最终日志位于 `artifacts/production-optimization/`。

当前没有通过更换音色、跳过物理/教学检查或猜测同步时间来提速。外部 AI/Fish 的响应时延与可用性仍需要服务端改善；本次没有宣称已通过整课真实配音和成片验收。

## 配置与观测

`VIDEO_STORYBOARD_BATCH_UTTERANCES` 默认 6（服务器最大 8），`VIDEO_STORYBOARD_BATCH_CHARACTERS` 默认 1000（最大 1600），`VIDEO_TTS_CONCURRENCY` 默认 2（仅支持 1–2，影响 Fish）。配置模板见 `.env.example`。

任务断点的 `metrics.calls` 保存最近 200 次请求的实际耗时、请求字节数、返回字符数、HTTP 状态及供应商返回的 token 用量；`requests`/`retries` 为累计传输计数，`contentCorrections` 单独统计内容纠正。历史断点累计阶段耗时含此前尝试，不能与当前任务墙钟混淆。界面百分比取后台真实进度，显示历时和等待继续状态。
